Today I've actually implemented the changes to pgd-proxy
configuration when reconfiguring from PGD5 to PGD6. The http
options move from pgd_proxy_options into the options for the
first bdr node group, which we must check exists and has the
name we expect as part of the upgrade. If they have been changed
at the per-node level, which seems unlikely to be a configuration
anyone is using, then we can just warn as we go that this is
no longer going to work.

We had an interesting bug surface today in the PEM team's testing;
it looked like a permission error at first, but really it turned
out to be a task that assumed that any node running the PEM agent
would have a postgres user - this isn't the case for barman nodes.
One of those that took some thinking to track down but once it's
understood is nice and easy to fix.

Another little bug we have is a race condition in AWS deployments -
if you abandon a half-finished provision, for example because you
realised you don't want this cluster while you're waiting for the
instances to come online, then you can end up with your ansible
inventory not written and if you try to deprovision the cluster
it doesn't deprovision the instances, which then manifests as a
failure to deprovision the security group because it still has
network interfaces in it. We should modernise that area of the
code to use newer ansible modules, but the easy fix is just to
re-run the provision and actually let it complete and write the
ansible inventory; then the deprovision will work.
